# OFFLINE-MODEL — Λειτουργία χωρίς σύνδεση

## 0. Τι ζητήθηκε (08/09) και τι ΔΕΝ ζητήθηκε

Ο συνεργάτης μπορεί να χάσει σύνδεση **κάποια στιγμή** (διαλείπον δίκτυο —
όχι ώρες χωρίς σήμα) και θέλει η εφαρμογή να μοιάζει native σε
tablet/κινητό. Ζητήθηκε ρητά και η δυνατότητα κάμερας για φωτογράφιση
ταυτότητας/χαρτιού πελάτη.

**Δεν ζητήθηκε** πλήρες offline-first με τοπική βάση δεδομένων
(«Επίπεδο 3» — συζητήθηκε και απορρίφθηκε ως overkill για αυτό το use
case: το `UserScope` επιβάλλεται server-side σε κάθε request, να το
καθρεφτίσεις τοπικά είναι επιφάνεια ασφαλείας χωρίς πραγματικό όφελος
εδώ).

Η κάμερα **υπάρχει ήδη** (`public/class-ecrm-shortcodes.php`, το
`data-camera` input με `capture="environment"`, 23/08) — δεν χρειάζεται
Capacitor/Cordova/native wrapper για αυτήν. Capacitor/TWA απορρίφθηκαν
γενικά: θα πρόσθεταν build pipeline και δεύτερο deployment target σε ένα
plugin που σήμερα δεν έχει κανένα build step (native ES modules,
versioning με `filemtime()` στο `asset_version()`), για μηδενικό
λειτουργικό κέρδος πέρα από αυτό που ήδη κάνει το PWA install.

## 1. Τι υπάρχει σήμερα (08/09, επιβεβαιωμένο από τον πραγματικό κώδικα)

- Καμία υποδομή PWA/offline: όχι service worker, όχι `manifest.json`, όχι
  `navigator.onLine`, όχι IndexedDB.
- Το shared `fetch()` (`ecrm-util.js`) **επιβάλλει** `cache: 'no-store'` +
  `Cache-Control: no-cache` στα δικά του REST calls — το αντίθετο από
  caching. `ecrm-form.js` και `ecrm-litsa.js` καλούν το raw `window.fetch`
  απευθείας, δεν περνούν καν από αυτό.
- `localStorage`: μόνο δύο ασήμαντα UI flags (`ecrm_sidebar`,
  `ecrm_nav_more`). Καμία επιχειρηματική τιμή τοπικά.
- Το nonce (`wp_create_nonce('wp_rest')`) τυπώνεται μία φορά, inline, στο
  `wp_footer` (`print_config()` στο `class-ecrm-shortcodes.php`). Ζει
  ~24 ώρες, είναι **ανά χρήστη**.
- `POST /contracts` (`ContractSaveController::save()`): αν
  `contract_id === 0` κάνει δημιουργία. **Καμία idempotency key
  οπουδήποτε στο project** (επιβεβαιώθηκε με grep σε όλο το `src/` και
  `public/assets/`) — retry ίδιου αιτήματος χωρίς αλλαγή θα δημιουργήσει
  δεύτερη σύμβαση.
- `POST /contracts/{id}/files` απαιτεί **υπάρχον** `id` — τα αρχεία δεν
  μπορούν να σταλούν πριν υπάρξει σύμβαση.
- `/customers/check` (έλεγχος διπλοεγγραφής) και `/extract` (AI εξαγωγή
  στοιχείων) είναι server-only ερωτήματα· δεν μπορούν να απαντηθούν
  offline με τίποτα.

## 2. Στρώματα — τι χτίζουμε και με ποια σειρά

Κάθε στρώμα είναι ανεξάρτητο commit. Αν σταματήσουμε μετά το (Α) ή το
(Β), υπάρχει ήδη πραγματική αξία — δεν είναι «μισή δουλειά».

### (Α) PWA shell — native εμφάνιση

`manifest.json` + εικονίδια + service worker που κάνει cache **μόνο**
static assets (JS modules, CSS) — ποτέ HTML, ποτέ REST απαντήσεις. Το
υπάρχον `asset_version()` (`filemtime()`) είναι ήδη ό,τι πρέπει: αλλαγμένο
αρχείο = αλλαγμένο URL = νέα εγγραφή cache, καμία επιπλέον λογική
invalidation. Δίνει εικονίδιο στην αρχική οθόνη, άνοιγμα χωρίς browser
UI, ταχύτερη φόρτωση των ίδιων των αρχείων. Μηδέν προσωπικά δεδομένα
αποθηκευμένα, μηδέν ρίσκο γύρω από το nonce.

**Μοντέλο: Sonnet.** Μηχανικό, καλά ορισμένο, χαμηλό ρίσκο — δεν αγγίζει
δεδομένα πελατών ή server-side λογική.

### (Β) Ανίχνευση σύνδεσης + τίμιο UI

`navigator.onLine` + `online`/`offline` events → μόνιμο banner «Εκτός
σύνδεσης». Σήμερα μια αποτυχία δικτύου δείχνει «Σφάλμα δικτύου» — ο
συνεργάτης το διαβάζει σαν «χάλασε», όχι σαν «είσαι offline, θα φύγει
μόλις γυρίσει». Καμία αποθήκευση δεδομένων εδώ ακόμα.

**Μοντέλο: Sonnet.** Καθαρό UI, καμία λογική συνέπειας δεδομένων.

### (Γ) Server: idempotency key + φρέσκο nonce

- `POST /contracts` δέχεται ένα `client_request_id` (uuid, παράγεται στον
  client). Ο server το κρατά (νέα στήλη ή μικρός πίνακας) και σε
  επανάληψη με το ίδιο key επιστρέφει το **αρχικό** `contract_id` αντί να
  ξαναδημιουργήσει.
- Νέο μικρό `GET` endpoint που επιστρέφει φρέσκο nonce, για χρήση πριν
  από κάθε replay.

Αυτό αξίζει να μπει **ανεξάρτητα** από το αν προχωρήσουμε στην ουρά
(Δ) — προστατεύει ήδη σήμερα από διπλά submit σε ασταθές δίκτυο (διπλό
κλικ, διπλό tap σε αργή σύνδεση).

**Μοντέλο: Opus.** Αγγίζει τον κύριο δρόμο δημιουργίας σύμβασης — λάθος
εδώ σημαίνει είτε διπλές συμβάσεις είτε χαμένες. Θέλει προσεκτική σκέψη
πάνω σε race conditions (δύο ταυτόχρονα requests με το ίδιο key) και στο
πώς συνδυάζεται με το υπάρχον `DraftExitGate`/lifecycle guards.

### (Δ) Η ουρά εγγραφής — client

Περιορισμένη στη ροή **νέας σύμβασης** (δημιουργία → αρχεία → status),
όχι σε κάθε εγγραφή του CRM:

- Αλυσίδα εξαρτήσεων με προσωρινό τοπικό id, αντικαθίσταται με το
  πραγματικό μόλις λυθεί η δημιουργία· σειριακά ανά σύμβαση.
- Φρέσκο nonce πριν από κάθε replay (μέσω του endpoint του (Γ)).
- Λήξη σύνδεσης (401/403 στο replay) → μήνυμα «Ξανασυνδέσου για να
  σταλούν N αιτήσεις σε αναμονή», ποτέ σιωπηλή απόρριψη, ποτέ ατέρμονο
  retry.
- Client στέλνει τη δική του χρονοσφραγίδα δημιουργίας· ο server την
  περιορίζει (ποτέ μελλοντική, ποτέ παράλογα παλιά) — τα ρολόγια
  κινητών λένε ψέματα.
- `/extract` και `/customers/check` μένουν ρητά εκτός ουράς — δεν
  προσφέρονται offline· ο συνεργάτης τα τρέχει κανονικά μόλις γυρίσει
  online.

**Μοντέλο: Opus.** Το πιο περίπλοκο κομμάτι: state machine με σειρά,
μερικές αποτυχίες, retry, και συνέπειες σε πραγματικά δεδομένα πελατών.
Λάθος εδώ δεν φαίνεται αμέσως — φαίνεται μήνες μετά σαν «ορφανή σύμβαση
χωρίς αρχεία» ή «διπλή σύμβαση» σε production.

### (Ε) Κύκλος ζωής PII στη συσκευή

Στην ουρά κάθονται φωτογραφίες ταυτοτήτων και ΑΦΜ πελατών, σε κινητό
συνεργάτη, ενδεχομένως για ώρες. Το project έχει ήδη προηγούμενο εδώ (το
ιστορικό της Λίτσας μεταφέρθηκε server-side, ~26/08, ρητά για λόγους
κρυπτογράφησης/PII). Χρειάζεται:

- TTL (π.χ. 48 ώρες) — μετά, η εγγραφή δείχνει «έληξε, ξαναστείλ' το»
  αντί να μένει επ' αόριστον.
- Καθάρισμα στο logout.
- Όριο μεγέθους/πλήθους εκκρεμών εγγραφών στην ουρά.

**Μοντέλο: Opus** για τον σχεδιασμό της απόφασης (TTL, όρια, τι σημαίνει
«καθάρισμα» — soft ή hard), **Sonnet** αρκεί για την υλοποίηση μόλις η
απόφαση είναι γραμμένη.

### (ΣΤ) Εργασία ελέγχου διπλοεγγραφής μετά τον συγχρονισμό

Ο έλεγχος `/customers/check` δεν τρέχει offline. Πρόταση: μετά το sync
τρέχει server-side αυτόματα, και αν χτυπήσει δημιουργείται εργασία για
τον συνεργάτη — ίδιος μηχανισμός με το `RejectionFollowUp`
(commit 255), όχι νέο κανάλι ειδοποίησης.

**Μοντέλο: Sonnet.** Ίδιο, ήδη γνωστό μοτίβο (`STATUS_CHANGED` listener
→ `TaskRepository::create()`), χαμηλό ρίσκο.

### (Ζ) Cache για διάβασμα — ξεχωριστή απόφαση, όχι μέρος αυτής της δουλειάς

Cache λιστών συμβολαίων/πελατών σημαίνει προσωπικά δεδομένα **πολλών**
πελατών αποθηκευμένα σε ένα κινητό — μεγάλο κόστος PII για σενάριο
(«φτιάχνω νέα σύμβαση») που δεν το χρειάζεται. Πρόταση προς συζήτηση
αργότερα: όχι καθόλου, ή το πολύ «οι τελευταίες Ν συμβάσεις που άνοιξε ο
ίδιος» με τους ίδιους κανόνες TTL/purge του (Ε). **Δεν ξεκινά χωρίς
ρητή απόφαση ιδιοκτήτη.**

## 3. Σύνοψη μοντέλων

| # | Στρώμα | Μοντέλο | Γιατί |
|---|--------|---------|-------|
| Α | PWA shell (manifest + SW για assets) | Sonnet | Μηχανικό, χαμηλό ρίσκο |
| Β | Ανίχνευση σύνδεσης + UI | Sonnet | Καθαρό UI |
| Γ | Idempotency key + fresh-nonce endpoint | **Opus** | Κύριος δρόμος δημιουργίας, race conditions |
| Δ | Client ουρά (create → files → status) | **Opus** | State machine, μερικές αποτυχίες, PII |
| Ε | PII lifecycle στη συσκευή | Opus (σχεδιασμός) / Sonnet (υλοποίηση) | Απόφαση ευαίσθητη, εκτέλεση μηχανική |
| ΣΤ | Task διπλοεγγραφής μετά sync | Sonnet | Γνωστό μοτίβο (RejectionFollowUp) |
| Ζ | Cache διαβάσματος | — | Δεν ξεκινά χωρίς ρητή απόφαση |

## 4. Τι ΔΕΝ κάνουμε

- Capacitor/Cordova/TWA — η κάμερα ήδη δουλεύει σαν web, δεν αξίζει το
  build pipeline.
- Πλήρες offline-first με τοπική βάση (Επίπεδο 3) — απορρίφθηκε, βλ. §0.
- Cache διαβάσματος (Ζ) πριν υπάρξει ρητή απόφαση για το PII κόστος.
