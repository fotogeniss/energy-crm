Πρόταση οθόνης — §1.8, πριν γραφτεί κώδικας

Energy CRM → Παρακολούθηση

Η Υγεία απαντά «τι δεν πάει καλά αυτή τη στιγμή». Δεν απαντά «πάει καλύτερα ή χειρότερα από την περασμένη εβδομάδα;» — και αυτή είναι διαφορετική ερώτηση, με διαφορετική απάντηση: μια πράσινη Υγεία μπορεί να κρύβει ένα cron που αστοχεί μία στις τρεις φορές, ή σφάλματα που τριπλασιάστηκαν από τότε που άλλαξε κάτι.

Τι μετρήθηκε πριν προταθεί αυτό. Το ErrorLog κρατά μόνο την τελευταία εμφάνιση κάθε κωδικού με έναν μετρητή — όχι πότε. Το Heartbeat (235) κρατά μόνο το τελευταίο run κάθε hook. Το BackupState (233) μόνο το τελευταίο αντίγραφο. Το rate-limit ζει σε transient που λήγει. Πουθενά στο plugin δεν υπάρχει ιστορικό λειτουργίας. Αρα το πάνω μισό αυτής της οθόνης δεν μπορεί να χτιστεί από υπάρχοντα δεδομένα — χρειάζεται νέα, μικρή αποθήκευση.
Τι ΔΕΝ χρειάζεται νέα αποθήκευση. Το κάτω μισό (πωλήσεις). Ο πίνακας contracts έχει ήδη created_at και ιστορικό καταστάσεων στον events· το AnalyticsRepository ήδη βγάζει μηνιαία σύνολα. Η διαφορά με την υπάρχουσα οθόνη Στατιστικά είναι η σκοπιά: εκείνη δείχνει «δικά μου / της ομάδας μου», αυτή δείχνει όλο το site και τη βλέπει μόνο ο διαχειριστής. Καμία διπλή υλοποίηση: ίδιο repository, άλλο scope.

Γιατί μόνο τόσα γραφήματα. Το energy-crm-product-bottleneck.md λέει «μία ειδοποίηση αξίζει όσο δέκα νέα γραφήματα». Ισχύει — γι' αυτό κάθε πλαίσιο εδώ απαντά σε ερώτηση που κάποιος θα έκανε («αστοχεί το cron;», «πότε ήταν το τελευταίο κενό στα backup;», «ανεβαίνουν τα σφάλματα;») και όχι σε ερώτηση που δείχνει ωραία. Τέσσερα πλαίσια σύστημα, τρία πωλήσεις. Τίποτα με πίτες, τίποτα με «engagement».

Πώς κρατιέται το ιστορικό (η μόνη αρχιτεκτονική απόφαση εδώ)

Νέος πίνακας {prefix}ecrm_metrics, τρεις στήλες: day DATE, metric VARCHAR(40), value INT, με PRIMARY KEY (day, metric). Η εγγραφή γίνεται πάντα με ένα INSERT … ON DUPLICATE KEY UPDATE value = value + N — ατομική στη MySQL, χωρίς read-modify-write, άρα χωρίς την κούρσα που θα είχε ένα option με πίνακα 90 ημερών μέσα του.

Γιατί όχι option. Ενα ecrm_metrics_history option θα χρειαζόταν διάβασμα-τροποποίηση-γράψιμο σε κάθε σφάλμα και σε κάθε cron· δύο ταυτόχρονα requests θα έχαναν το ένα τη μέτρηση του άλλου, σιωπηλά. Και η ερώτηση «πόσα σφάλματα την ημέρα Χ» θα γινόταν PHP loop πάνω σε ολόκληρο το ιστορικό αντί για ένα WHERE day BETWEEN.

Ογκος: ~6 metrics × 1 γραμμή/ημέρα = ~2.200 γραμμές/έτος. Η διατήρηση (180 ημέρες, φιλτραρίσιμο) μπαίνει στο ήδη υπάρχον ημερήσιο σάρωμα Retention — καμία νέα cron εργασία.

Πού γράφεται (τρία σημεία, μία γραμμή το καθένα): ErrorLog::record() → errors· Heartbeat::mark() → cron:<hook>· BackupState::record() → backup. Καμία αλλαγή στη συμπεριφορά τους — μόνο μία επιπλέον καταγραφή.

Καμία νέα κατηγορία δεδομένων για το GDPR. Ο πίνακας κρατά μόνο αριθμούς ανά ημέρα. Κανένα user_id, καμία διαδρομή, κανένα μήνυμα — τίποτα που να συνδέεται με πρόσωπο, άρα τίποτα να εξαχθεί ή να διαγραφεί.

Πού ζει η οθόνη: wp-admin, υπομενού δίπλα στην Υγεία, manage_options — όπως η Υγεία. Το πάνω μισό είναι εσωτερικά του συστήματος και δεν έχει λόγο να φαίνεται σε συνεργάτη· το κάτω μισό είναι όλο το site, δηλαδή ούτως ή άλλως όψη ιδιοκτήτη.

Τι ΔΕΝ μπαίνει, και γιατί

Ζωντανό «τι τρέχει τώρα». Θα ήθελε polling ή WebSocket για ερώτηση που η Υγεία ήδη απαντά με ένα refresh.
Γραφήματα rate-limit. Το rate-limit χτυπά όταν κάποιος κάνει κατάχρηση — αυτό είναι ειδοποίηση, όχι γράφημα· ανήκει στη λογική του (234).
Πίτες κατανομών. Οι κατανομές υπάρχουν ήδη στα Στατιστικά, ως μπάρες που διαβάζονται. Δεύτερο αντίγραφο σε άλλο σχήμα δεν προσθέτει πληροφορία.
Εξαγωγή σε CSV. Πριν ζητηθεί. Αν χρειαστεί, είναι μία διαδρομή REST πάνω στον ίδιο πίνακα.
