# Energy CRM — Δοκιμές

Δύο σουίτες, με διαφορετική δουλειά.

| | `composer test` | `composer test:integration` |
|---|---|---|
| Τι φορτώνει | τίποτα | πραγματικό WordPress + MySQL |
| Τι ελέγχει | κανόνες domain | scope, SQL, κρυπτογράφηση, διαγραφή |
| Χρόνος | < 1 δευτ. | δευτερόλεπτα |
| Στο pre-commit hook | ναι | όχι |

Το `composer check` τρέχει μόνο την πρώτη. Αυτό είναι σκόπιμο: κάποιος που δεν
έχει στήσει βάση πρέπει να μπορεί να κάνει commit. Το `composer check:all`
τρέχει και τις δύο.

## Γιατί υπάρχει η δεύτερη

Τα unit tests δεν φορτώνουν WordPress, και αυτός ο περιορισμός κράτησε τον
domain κώδικα καθαρό. Αυτό που δεν φτάνουν είναι το σημείο όπου ζουν τα χρήματα
και τα προσωπικά δεδομένα: αν ένα query **πράγματι** αποκλείει τις συμβάσεις
άλλου συνεργάτη, αν μια κρυπτογραφημένη στήλη **πράγματι** επιστρέφει
αναγνώσιμη, αν η διαγραφή **πράγματι** δεν αφήνει τίποτα πίσω.

Αυτά είναι ισχυρισμοί για SQL και για WordPress. Μόνο πραγματική βάση τους
κρίνει. Το `UserScope` ως υποχρεωτικό όρισμα εγγυάται ότι περνιέται — όχι ότι
το SQL το χρησιμοποιεί.

## ⚠ Η βάση διαγράφεται

Η βιβλιοθήκη δοκιμών του WordPress κάνει **DROP σε κάθε πίνακα** της βάσης που
θα της δείξεις, σε κάθε εκτέλεση. Στραμμένη στη βάση του site θα έσβηνε κάθε
πελάτη, σύμβαση και υπογραφή.

Γι' αυτό δεν υπάρχει προεπιλογή. Το bootstrap σταματάει αν δεν έχεις ονομάσει
βάση ρητά, και αρνείται αν το όνομα ταιριάζει με αυτό του `wp-config.php`.

## Στήσιμο

**1. Εγκατάστησε τα εργαλεία**

```
composer update
```

Φέρνει τα `wp-phpunit/wp-phpunit` και `yoast/phpunit-polyfills`.

**2. Φτιάξε βάση μιας χρήσης**

Στο Local, άνοιξε το Adminer (Database → Open Adminer) και δημιούργησε βάση με
όνομα `energy_crm_tests`. Ή από γραμμή εντολών:

```
mysql -u root -proot -e "CREATE DATABASE energy_crm_tests"
```

**3. Δήλωσε πού είναι**

Windows, στο ίδιο παράθυρο όπου θα τρέξεις τα tests:

```
set ECRM_TEST_DB_NAME=energy_crm_tests
set ECRM_TEST_DB_USER=root
set ECRM_TEST_DB_PASSWORD=root
set ECRM_TEST_DB_HOST=127.0.0.1
```

macOS / Linux:

```
export ECRM_TEST_DB_NAME=energy_crm_tests
export ECRM_TEST_DB_USER=root
export ECRM_TEST_DB_PASSWORD=root
export ECRM_TEST_DB_HOST=127.0.0.1
```

Τα στοιχεία σύνδεσης του Local τα βρίσκεις στο Site → Database. Η θύρα δεν
είναι πάντα η 3306· αν διαφέρει, δώσ' την ως `127.0.0.1:10005`.

**4. Τρέξε**

```
composer test:integration
```

## Ένα script, ώστε να μη ξαναπεραστούν με το χέρι

```
tools\test-db.cmd        μόνο τα integration
tools\test-db.cmd all    phpcs + phpstan + unit + integration
```

Μέσα από το **Site Shell** του Local, όχι από σκέτο `cmd`.

Το `set` του cmd.exe ζει **μόνο σε εκείνο το παράθυρο**. Κάθε φορά που ανοίγεις
νέο Site Shell, το `ECRM_TEST_DB_NAME` λείπει ξανά και το bootstrap σταματά — που
είναι το σωστό, αλλά μοιάζει με «χάλασε κάτι». Δεν χάλασε: απλώς δεν υπάρχει
default, γιατί ό,τι μπει εκεί **διαγράφεται ολόκληρο**.

Τα στοιχεία σύνδεσης **δεν είναι γραμμένα μέσα στο script.** Τα ρωτάει από το
ίδιο το WordPress (`wp config get DB_HOST` κ.λπ.), ώστε να μη σαπίσουν όταν
αλλάξει η θύρα του Local — που αλλάζει, και δεν είναι πάντα η 3306.

## Όταν βγάζει σφάλμα

| τι λέει | τι σημαίνει | τι κάνεις |
|---|---|---|
| `No test database named` | δεν δηλώθηκε `ECRM_TEST_DB_NAME` — συνήθως επειδή είναι **νέο παράθυρο** | `tools\test-db.cmd` |
| `is the site's own database` | το δίχτυ έπιασε. **Καλώς.** Θα έσβηνε κάθε πελάτη | δώσε άλλο όνομα βάσης |
| `Unknown database 'energy_crm_tests'` | δεν φτιάχτηκε ποτέ | το script τη φτιάχνει· αλλιώς Adminer → `CREATE DATABASE energy_crm_tests;` |
| `Access denied for user` | άλλος χρήστης/κωδικός από του site | `wp config get DB_USER` και `DB_PASSWORD`, και δώσ' τα ρητά |
| `Undefined constant WP_TESTS_DOMAIN` | η **δεύτερη** διεργασία PHP δεν βρήκε το config | δες παρακάτω: `ECRM_TEST_PHP_BINARY` |
| `EXIT=0` **χωρίς καθόλου output από το phpunit** | το `vendor/bin/phpunit` είναι **0 bytes** — έχει ξανασυμβεί | `composer reinstall phpunit/phpunit`. Το `composer install` λέει «Nothing to install» και **δεν** το διορθώνει. §3 του HANDOVER |
| το script τυπώνει την **κεφαλίδα** και γυρίζει σιωπηλά στο prompt | `.bat` που καλεί `.bat` **χωρίς `call`** παραδίδει τον έλεγχο και δεν τον ξαναπαίρνει | διορθωμένο· αν το ξαναδείς σε δικό σου script, βάλε `call` πριν από `wp`, `composer`, `phpcs` |

Οι δύο τελευταίες είναι οι επικίνδυνες, γιατί μοιάζουν με επιτυχία. **Ο μόνος
έλεγχος που μετράει:** αν δεν είδες τη γραμμή `OK (311 tests, 2047 assertions)`,
τα integration **δεν έτρεξαν**. Ούτε ο κωδικός εξόδου ούτε η απουσία κόκκινου το
λένε αυτό — μόνο η γραμμή.

Και προσοχή σε κάτι που έχει ήδη περάσει από κάτω: το **pre-commit hook τρέχει
`composer check`, χωρίς integration**. Ένα commit που περνά δεν σημαίνει ότι
τρέξανε. Γι' αυτό το `check:all` είναι χωριστό και τρέχει με το χέρι, πριν το
commit.

## Πού βρίσκει το WordPress

Από τη διαδρομή του plugin, ανεβαίνοντας τρία επίπεδα
(`wp-content/plugins/energy-crm` → ρίζα του site). Αν το δικό σου στήσιμο
διαφέρει, δώσε `ECRM_TEST_WP_ROOT`.

Αν το `php` δεν είναι στο PATH των Windows — συνηθισμένο με το Local, που
κουβαλά δικό του binary — δώσε τη διαδρομή:

```
set ECRM_TEST_PHP_BINARY=C:\Program Files (x86)\Local\resources\extraResources\lightning-services\php-8.2.x\bin\win64\php.exe
```

Χρειάζεται επειδή το WordPress εγκαθιστά τη βάση δοκιμών **ξεκινώντας
ξεχωριστή διεργασία PHP**. Γι' αυτό οι ρυθμίσεις ζουν σε αρχείο
(`tests/Integration/wp-tests-config.php`) και όχι ως σταθερές μέσα στο
bootstrap: η δεύτερη διεργασία δεν κληρονομεί τίποτα.

## Τι καλύπτεται σήμερα

- **`ContractScopeTest`** — ότι ένας συνεργάτης δεν διαβάζει και δεν γράφει
  σύμβαση άλλου, ότι ο διαχειριστής ομάδας φτάνει το downline του και όχι πιο
  πέρα, ότι η ιδιοκτησία δεν ορίζεται από το payload. Η κατηγορία IDOR που
  έκλεισε στο βήμα 2 του roadmap και τίποτα δεν την κρατούσε κλειστή.
- **`EncryptedCustomerColumnsTest`** — ότι το ΑΦΜ είναι δυσανάγνωστο στον δίσκο
  και αναγνώσιμο μέσω repository, ότι οι στήλες αναφορών μένουν καθαρές, ότι
  παλιές γραμμές σε καθαρό κείμενο εξακολουθούν να διαβάζονται, ότι το blind
  index βρίσκει διπλοεγγραφή, ότι το hash δεν φεύγει ποτέ από το Persistence.
- **`PersonalDataErasureTest`** — κάθε πίνακας που είχε ξεχαστεί μία φορά.
  Τελειώνει με έλεγχο που σαρώνει όλες τις στήλες όλων των σχετικών γραμμών για
  το όνομα του πελάτη: αν προστεθεί πίνακας και δεν προστεθεί στον eraser, εδώ
  φαίνεται.
- **`RestRouteGuardTest`** — δεν ονομάζει endpoints. Ρωτάει τον `WP_REST_Server`
  τι είναι καταχωρημένο στο `ecrm/v1` και απαιτεί από κάθε route να έχει
  `permission_callback`, να είναι **κλητό**, και να αρνείται ανώνυμο (401) και
  συνδεδεμένο χωρίς ρόλο CRM (403). Εξαίρεση μόνο η λίστα `PUBLIC_ROUTES`, όπου
  κάθε εγγραφή κουβαλά τον λόγο της. Ένα route που θα γραφτεί αύριο καλύπτεται
  από την πρώτη μέρα.
- **`ContractRestAccessTest`** — το ίδιο IDOR με το `ContractScopeTest`, αλλά
  μέσα από `rest_do_request`: guard, σχήμα `args`, `ScopeResolver` και
  controller μαζί. Ο ξένος συνεργάτης παίρνει **την ίδια απάντηση** με ένα id
  που δεν υπήρξε ποτέ, και η ικανότητα διαχωρίζεται ρητά από το scope
  (Συνεργάτης με `ecrm_delete_contract` περνά την πρώτη πύλη και σταματά στη
  δεύτερη).

## Γιατί δεν χρησιμοποιείται το `WP_UnitTestCase`

Η προφανής βασική κλάση καλεί `PHPUnit\Util\Test::parseTestMethodAnnotations()`,
που καταργήθηκε στο PHPUnit 10. Η βιβλιοθήκη δοκιμών του WordPress στοχεύει
ακόμη το 9· το project τρέχει 11, γιατί η unit σουίτα χρησιμοποιεί attributes
που το 9 δεν διαβάζει.

Αυτό που πράγματι προσφέρει το `WP_UnitTestCase` και μας χρειάζεται είναι
μικρό: μία συναλλαγή ανά test και ένας τρόπος να φτιάχνεις χρήστη. Και τα δύο
είναι λίγες γραμμές στο `IntegrationTestCase`. Το WordPress φορτώνεται κανονικά
— μόνο η test case είναι δική μας.

## Τι δεν καλύπτεται ακόμη

Το **σώμα** των απαντήσεων. Η σάρωση κρίνει ποιος μπαίνει, όχι τι παίρνει όποιος
μπήκε: ότι το `/contracts/{id}` δεν επιστρέφει στήλες που δεν έπρεπε, ότι ένα
σφάλμα δεν διαρρέει SQL ή διαδρομές δίσκου. Επόμενο βήμα, αν χρειαστεί.

Επίσης αδοκίμαστες οι **δημόσιες** διαδρομές από την πλευρά του πελάτη: το
`/sign/{token}` και το `/track/{token}` εξαιρούνται ρητά από τη σάρωση, οπότε
κανείς δεν ελέγχει σήμερα ότι ένα άκυρο token απαντά το ίδιο με ένα
χρησιμοποιημένο. Ο κώδικας το κάνει σκόπιμα (βλ. `SigningController`) — απλώς
δεν το κρατά τίποτα κλειστό.
