# ΚΡΙΣΙΜΑ — τα χρήματα

## 1. Δύο εκκαθαρίσεις μπορούν να πληρώσουν τις ίδιες συμβάσεις

`admin/class-ecrm-payouts.php:149-170`

```php
$rows = self::unsettled_rows( $partner );      // SELECT ... WHERE payout_id IS NULL
...
$wpdb->insert( $pt, [...] );                    // νέα παρτίδα
$payout_id = (int) $wpdb->insert_id;
$wpdb->query( $wpdb->prepare( "UPDATE {$ct} SET payout_id = %d WHERE id IN ($in)", $payout_id ) );
```

Διάβασμα, μετά γράψιμο, **χωρίς transaction και χωρίς συνθήκη στο UPDATE**.

**Σενάριο:** ο διαχειριστής πατάει «Δημιουργία εκκαθάρισης» και η σελίδα αργεί· ξαναπατάει. Ή δύο διαχειριστές δουλεύουν ταυτόχρονα. Και τα δύο αιτήματα διαβάζουν τις ίδιες 40 ασυμψήφιστες συμβάσεις, και τα δύο περνούν το `INSERT`. Δημιουργούνται **δύο παρτίδες** με `cnt = 40` και το ίδιο ποσό. Το δεύτερο `UPDATE` γράφει το δικό του `payout_id` πάνω από το πρώτο, αλλά **η πρώτη παρτίδα υπάρχει ακόμα** στην οθόνη Εκκαθαρίσεις, με ποσό και πλήθος. Μαρκάρονται και οι δύο «Πληρώθηκε» → **ο συνεργάτης πληρώνεται δύο φορές**.

**Η διόρθωση την ξέρει ήδη ο κώδικας.** Το `SignatureRepository::sign()` (γρ. 89-107) λέει: *«"Ήδη υπογεγραμμένο" είναι μέρος του WHERE και όχι έλεγχος πριν από αυτό: δύο υποβολές που φτάνουν μαζί δεν πρέπει να πετύχουν και οι δύο.»* Ακριβώς το ίδιο μοτίβο χρειάζεται εδώ:

```php
$affected = $wpdb->query( $wpdb->prepare(
    "UPDATE {$ct} SET payout_id = %d
     WHERE id IN ($in) AND (payout_id IS NULL OR payout_id = 0)", $payout_id ) );
```

…και μετά **ξαναϋπολόγισε** `cnt`/`amount` από τα `$affected`, ή σβήσε την παρτίδα αν `$affected === 0`. Το μοτίβο εφαρμόστηκε εκεί που το ρίσκο είναι μια υπογραφή, και δεν εφαρμόστηκε εκεί που το ρίσκο είναι λεφτά.

## 2. Η «ακύρωση» παρτίδας σβήνει και πληρωμένη εκκαθάριση

`admin/class-ecrm-payouts.php:185-196`

```php
public static function remove(): void {
    ...
    $wpdb->query( "UPDATE {$ct} SET payout_id = NULL WHERE payout_id = %d" );
    $wpdb->delete( ECRM_DB::table( 'payouts' ), [ 'id' => $id ] );
}
```

**Καμία εξέταση του `status`.** Μια παρτίδα με `status = 'paid'` και `paid_at` συμπληρωμένο διαγράφεται όπως κάθε άλλη.

**Σενάριο:** πληρώνεται η εκκαθάριση Ιουλίου. Τον Αύγουστο κάποιος πατάει «Διαγραφή» σε λάθος γραμμή. Οι 40 συμβάσεις γυρίζουν σε ασυμψήφιστες, **η απόδειξη ότι πληρώθηκαν εξαφανίζεται**, και η επόμενη εκκαθάριση τις ξαναπληρώνει. Δεν υπάρχει κανένα ίχνος: το `payouts` δεν έχει soft-delete και το `events` δεν καταγράφει εκκαθαρίσεις.

Και το `pay()` (γρ. 174-183) δεν ελέγχει ούτε ότι η παρτίδα υπάρχει ούτε ότι είναι `pending` — `$wpdb->update` σε ανύπαρκτο id δεν κάνει τίποτα σιωπηλά, και ο χρήστης βλέπει «Πληρώθηκε».

**Διόρθωση:** το `remove()` να αρνείται όταν `status = 'paid'` (ή να απαιτεί χωριστή «αντιλογιστική» ενέργεια που αφήνει ίχνος), και το `pay()` να γράφει με `WHERE id = %d AND status = 'pending'` και να ελέγχει τις επηρεασμένες γραμμές.

## 3. Το ποσό προμήθειας δεν είναι ντετερμινιστικό

`admin/class-ecrm-commissions.php:36,45`

```php
$rules = $wpdb->get_results( "SELECT * FROM {$rt} WHERE active = 1", ARRAY_A );  // χωρίς ORDER BY
...
if ( $score > $best_score ) { $best_score = $score; $best = $r; }                 // ισοβαθμία → ο πρώτος
```

Δύο ενεργοί κανόνες με **την ίδια ειδικότητα** (π.χ. και οι δύο μόνο με `provider_id`, με διαφορετικά ποσά — τίποτα στη φόρμα δεν το εμποδίζει) δίνουν ίδιο `$score`. Νικάει όποιος έρθει πρώτος. **Η MySQL δεν εγγυάται σειρά χωρίς `ORDER BY`** — μπορεί να αλλάξει μετά από `OPTIMIZE TABLE`, αλλαγή πλάνου ή απλή διαγραφή γραμμής.

**Συνέπεια:** ο συνεργάτης βλέπει €12 στην οθόνη του, η εκκαθάριση υπολογίζει €10. Και τα δύο «σωστά», σε διαφορετική στιγμή.

**Δεύτερο, χωριστό λάθος στην ίδια συνάρτηση — η βαθμολογία δεν μετράει ειδικότητα:**

| Κανόνας | Score |
|---|---|
| μόνο `provider_id` | 8 |
| `program_id` + `energy_type` + `category` | 4+2+1 = **7** |

Ένας κανόνας «όλοι οι πάροχοι, αυτό το συγκεκριμένο πρόγραμμα, οικιακό ρεύμα» **χάνει** από τον γενικό κανόνα του παρόχου — παρότι ταιριάζει σε πολύ λιγότερες συμβάσεις. Η φόρμα επιτρέπει ρητά «Πάροχος: Όλοι» με επιλεγμένο πρόγραμμα (γρ. 94-99), οπότε δεν είναι θεωρητικό. Το κείμενο της οθόνης υπόσχεται *«ο πιο ειδικός κανόνας υπερισχύει»*· ο κώδικας υλοποιεί σειρά προτεραιότητας πεδίων, όχι ειδικότητα.

**Διόρθωση:** `ORDER BY id DESC` (ή ρητή στήλη `priority`) για ντετερμινιστική ισοβαθμία, και επανεξέταση των βαρών ώστε το `program_id` να μετράει τουλάχιστον όσο το `provider_id`.

## 4. Καμία επιστροφή προμήθειας

`admin/class-ecrm-payouts.php:42` — `unsettled_rows()` πιάνει μόνο `payout_id IS NULL`. Μόλις μια σύμβαση σφραγιστεί με `payout_id`, **τίποτα δεν την ξανακοιτάζει ποτέ**.

`ContractStatus::allowedNext()` επιτρέπει `routed → cancelled`, `routed → terminated`, `active → terminated`. Δηλαδή μια σύμβαση μπορεί κάλλιστα να πληρωθεί και μετά να πεθάνει.

**Και οι δύο οθόνες διαφωνούν μεταξύ τους:** το `CommissionRepository::payable()` φιλτράρει με την **τρέχουσα** κατάσταση, οπότε η ακυρωμένη σύμβαση εξαφανίζεται από το σύνολο του συνεργάτη· η παρτίδα όμως εξακολουθεί να την περιέχει και να την έχει πληρώσει. Κανείς δεν ειδοποιείται.

Αυτό είναι απόφαση επιχείρησης, όχι μόνο κώδικα — αλλά αυτή τη στιγμή η απόφαση έχει ληφθεί σιωπηλά, υπέρ του «δεν παίρνουμε πίσω».

# ΥΨΗΛΑ

## 5. Δύο υλοποιήσεις του «τι βλέπει ποιος», που διαφωνούν

| | `WordPressScopeResolver::resolve()` <br>`src/Access/WordPressScopeResolver.php:48-59` | `ECRM_DB::visible_user_ids()` <br>`includes/class-ecrm-db.php:404-414` |
|---|---|---|
| διαχειριστής | όλα | όλα |
| **χωρίς `ecrm_manage_team`** | **μόνο ο εαυτός** | **όλο το υποδέντρο** |
| με `ecrm_manage_team` | υποδέντρο | υποδέντρο |

Το `ecrm_manage_team` ελέγχεται σε **ένα ακριβώς σημείο σε όλο τον κώδικα** — τη γραμμή 54 του `WordPressScopeResolver`. Η παλιά συνάρτηση δεν το ρωτάει καθόλου.

Χρήστες της παλιάς:
- `includes/class-ecrm-files.php:155` — ποιος μπορεί να κατεβάσει ένα σαρωμένο δελτίο ταυτότητας
- `includes/class-ecrm-import.php:204` — ποιες συμβάσεις πειράζει το Excel του παρόχου

**Σήμερα δεν εκμεταλλεύεται:** ο ρόλος Συνεργάτης έχει και `MANAGE_TEAM` και `IMPORT_DATA`· ο Πωλητής και ο Καταχωρητής δεν έχουν `IMPORT_DATA`. Άρα οι δύο απαντήσεις συμπίπτουν **με το τρέχον `Roles::matrix()`**.

**Γιατί είναι ύψηλο παρόλα αυτά:** το ίδιο το `Roles.php:18` λέει *«Αν αυτό δεν ταιριάζει με το πώς δουλεύει η εταιρεία, άλλαξε το `matrix()` και ανέβασε το VERSION· τίποτα άλλο δεν χρειάζεται να κουνηθεί.»* Αυτή η υπόσχεση **δεν ισχύει**. Αφαίρεσε το `MANAGE_TEAM` από τον Συνεργάτη κρατώντας το `IMPORT_DATA`, ή δώσε `IMPORT_DATA` στον Πωλητή, και ένας συνεργάτης με ομάδα από κάτω αποκτά πρόσβαση σε ταυτότητες και συμβάσεις που η εφαρμογή αρνείται να του δείξει. Η αλλαγή θα φαίνεται ασφαλής και θα περάσει από review.

Και είναι ακριβώς αυτό για το οποίο γράφτηκε το `ScopeClause`: *«ένα διπλασιασμένο clause εξουσιοδότησης είναι το ίδιο λάθος με καλύτερα ρούχα»*.

**Διόρθωση:** το `visible_user_ids()` να καλεί τον `ScopeResolver` (`Services::scopes()->forUser($uid)->userIds()`), όχι το `NetworkRepository` απευθείας.

## 6. Οι διαδρομές `/sign/{token}` είναι ορφανές — και ζωντανές

**Κανένα σημείο του κώδικα δεν κάνει INSERT στον πίνακα `signatures`** (πλην των tests). Το `SignLinkController` το λέει ρητά στη γραμμή 6: *«Ο σύνδεσμος είναι το συνηθισμένο tracking URL... δεν υπάρχει δεύτερο token να λήξει ή να διαρρεύσει.»*

Ο `SigningController` όμως καταχωρεί ακόμα δύο δημόσιες διαδρομές (`src/Http/SigningController.php:51-70`, `permission_callback => '__return_true'`), και το `public/class-ecrm-sign-page.php:34` διαβάζει τον ίδιο πίνακα.

Σύγκριση με τη ζωντανή διαδρομή υπογραφής (`ECRM_Tracking::rest_sign`):

| | `ECRM_Tracking::rest_sign` | `SigningController::store` |
|---|---|---|
| rate limit | ✔ `track_sign` 10/600 | **✘ κανένα** |
| έλεγχος PNG magic bytes | ✔ `\x89PNG\r\n\x1a\n` | **✘** |
| υπερμέγεθες | ✔ **απορρίπτει** >800KB | **✘ κόβει** στα 600.000 bytes |
| έλεγχος κατάστασης | ✔ `signable_statuses()` | **✘** |
| απαίτηση συναίνεσης | ✔ | **✘** |
| λήξη token | — (stateless HMAC) | **✘ ποτέ** |

Δύο συγκεκριμένες συνέπειες:

**α) Παρακάμπτεται ο γράφος μεταβάσεων.** `SigningController.php:123-124`:
```php
$this->lifecycle->moveTo($contractId, 'signed', [ 'from' => null, ... ]);
```
Στο `ContractLifecycle::moveTo()` (γρ. 81-97), το `array_key_exists('from', ...)` είναι **true**, οπότε `$from = (string) null = ''`, οπότε `ContractStatus::tryFromSlug('')` δίνει `null`, οπότε ο έλεγχος `canMoveTo()` **δεν εκτελείται καθόλου**. Το docblock του `ContractStatus` υπόσχεται *«Άρνηση σε ό,τι δεν επιτρέπει η ροή: αναβίωση ακυρωμένης σύμβασης»*. Μια ακυρωμένη σύμβαση με έγκυρο token υπογράφεται κανονικά.

Το ίδιο το `moveTo()` λέει «οι διαδρομές υπογραφής περνούν `null` γιατί πραγματικά δεν ξέρουν». Σωστό — αλλά «δεν ξέρω από πού έρχεται» και «μην εφαρμόσεις κανένα κανόνα» δεν είναι το ίδιο πράγμα.

**β) Η κομμένη υπογραφή χάνεται σιωπηλά.** Γρ. 112: `$image = substr($image, 0, self::MAX_IMAGE_BYTES);`. Ένα κομμένο base64 δίνει `base64_decode(..., true) === false` στη γρ. 153 → η `storeSignatureImage()` επιστρέφει χωρίς να γράψει τίποτα. Η σύμβαση όμως έχει ήδη μαρκαριστεί υπογεγραμμένη και το `DocumentQueue::enqueue()` τρέχει. Αποτέλεσμα: **σύμβαση σε κατάσταση «Υπεγράφη» χωρίς εικόνα υπογραφής**, και η φόρμα του παρόχου τυπώνεται με κενό πλαίσιο.

**Διόρθωση:** αν ο παλιός μηχανισμός έχει αποσυρθεί, να φύγουν οι διαδρομές και το `class-ecrm-sign-page.php`. **Χρειάζεται έλεγχος στην παραγωγή πρώτα:**

```sql
SELECT COUNT(*), MIN(created_at), MAX(created_at),
       SUM(signed_at IS NULL) AS aneksofliti
FROM wp_ecrm_signatures;
```

Κάθε γραμμή με `signed_at IS NULL` είναι ένα διαπιστευτήριο υπογραφής που δεν λήγει ποτέ, δεν έχει rate limit και παρακάμπτει τον γράφο.

## 7. Το Excel import παρακάμπτει τον `ContractLifecycle`

`includes/class-ecrm-import.php:232-242`

```php
$wpdb->update( $ct, [ 'status' => $status ], [ 'id' => (int) $row['id'] ] );
$wpdb->insert( ECRM_DB::table( 'events' ), [ ... ] );
```

Είναι **το μοναδικό σημείο σε όλο τον κώδικα** που γράφει `status` εκτός του `ContractTransitions::applyTransition()`. (Το επιβεβαίωσα με σάρωση: όλες οι υπόλοιπες 8 διαδρομές αλλαγής κατάστασης περνούν από `moveTo()`.)

Το `ContractLifecycle` δηλώνει στη γραμμή 4: *«Κάθε αλλαγή κατάστασης περνά από εδώ... Πέντε καλούντες, μία συμπεριφορά.»* Το import είναι ο έκτος και δεν περνά.

Τι χάνεται σε κάθε γραμμή του Excel:

1. **Ο γράφος μεταβάσεων** — `cancelled → active` περνάει κανονικά. Ένας πάροχος που στέλνει λάθος γραμμή στο Excel του ανασταίνει ακυρωμένες συμβάσεις, και οι καταστάσεις `routed`/`active`/`resolved` είναι πληρωτέες (`ContractStatus::isPayable()`).
2. **`ECRM_Notifications::notify_status_change()`** — ο συνεργάτης δεν βλέπει τίποτα στο καμπανάκι.
3. **`ECRM_Messaging::on_status_change()`** — **ο πελάτης δεν παίρνει SMS**, ενώ η ίδια ακριβώς μετάβαση από το UI του στέλνει.
4. **`do_action(ContractLifecycle::STATUS_CHANGED)`** — ο `AutoProcess` δεν ενεργοποιείται ποτέ για εισαγόμενες αλλαγές.

Το (3) είναι το χειρότερο επιχειρησιακά: η κύρια ροή ενημέρωσης καταστάσεων στην πράξη είναι το Excel του παρόχου, και είναι ακριβώς η ροή που δεν ειδοποιεί κανέναν.

**Διόρθωση:** αντικατάσταση των δύο γραμμών με `Services::lifecycle()->moveTo( (int) $row['id'], $status, [ 'user_id' => $uid, 'from' => $row['status'], 'message' => 'Ενημέρωση από Excel παρόχου', 'sms' => false ] )` — και το `moveTo` επιστρέφει `false` όταν η ροή αρνείται, οπότε η αναφορά μπορεί επιτέλους να πει «3 απορρίφθηκαν» αντί να τις μετρήσει ως ενημερωμένες. (Το `sms` το αφήνω στην κρίση σου: 200 SMS με μία εισαγωγή είναι ίσως χειρότερο από κανένα.)

## 8. Η απόδειξη συναίνεσης δείχνει το Cloudflare

Το `src/Infrastructure/ClientIp.php` είναι εξαιρετικό: εμπιστεύεται μόνο ρητά δηλωμένους proxies, διαβάζει την αλυσίδα `X-Forwarded-For` **από δεξιά**, με σωστό CIDR matching σε IPv4 και IPv6, πλήρως unit-tested.

**Έχει έναν και μόνο καλούντα:** `includes/class-ecrm-ratelimit.php:46`.

Τα τρία σημεία που καταγράφουν IP **ως νομικό τεκμήριο** το αγνοούν:

| Αρχείο | Γραμμή | Στήλη |
|---|---|---|
| `src/Http/ContractSaveMapping.php` | 198-202 | `consent_ip` |
| `src/Http/SigningController.php` | 114 | `signed_ip` |
| `public/class-ecrm-tracking.php` | 212 | `signed_ip` |

Και τα τρία: `$_SERVER['REMOTE_ADDR']` κατευθείαν.

**Σενάριο:** το site μπαίνει πίσω από Cloudflare — που ο ίδιος ο κώδικας το προβλέπει, το `HTTP_CF_CONNECTING_IP` είναι ονομασμένη σταθερά. Από εκείνη τη στιγμή **κάθε** συναίνεση και **κάθε** υπογραφή καταγράφει την ίδια διεύθυνση: του edge node. Το CHANGELOG χαρακτηρίζει το `consent_ip` *«η απόδειξη συναίνεσης του GDPR»*. Απόδειξη που δείχνει το Cloudflare δεν είναι απόδειξη, και το χειρότερο είναι ότι δεν σπάει τίποτα — απλώς γεμίζει η στήλη με λάθος τιμή και κανείς δεν το μαθαίνει μέχρι να χρειαστεί.

**Διόρθωση:** ένας helper `Services::clientIp()->resolve($_SERVER)` και τα τρία σημεία να τον καλούν. Είναι η μόνη διόρθωση της λίστας που είναι κυριολεκτικά τριών γραμμών.

## 9. Η προστασία των εγγράφων δεν καλύπτει nginx

`includes/class-ecrm-files.php:28-48` — ο φάκελος `uploads/ecrm-secure` θωρακίζεται με `.htaccess` (Apache), `web.config` (IIS) και `index.php`.

**Δεν υπάρχει τίποτα για nginx** — και το Local by Flywheel, με το οποίο αναπτύσσεται αυτό, τρέχει nginx εξ ορισμού.

Υπό nginx ο φάκελος σερβίρεται απευθείας. Ό,τι απομένει είναι η μη-μαντεψιμότητα του ονόματος: `'doc_' . wp_generate_password(24, false) . '.' . $ext` (γρ. 108) — 24 χαρακτήρες, ~140 bits. **Πρακτικά κρατάει.** Αλλά:

- η `X-Content-Type-Options`, το `Content-Disposition` και ο έλεγχος εξουσιοδότησης της `serve()` **δεν εφαρμόζονται** στην απευθείας διαδρομή·
- ένα όνομα αρχείου που διέρρευσε (screenshot, referer, log, backup) γίνεται μόνιμος δημόσιος σύνδεσμος **χωρίς λήξη**, ενώ μέσω `serve()` το token ζει 1 ώρα·
- αν κάποια στιγμή ενεργοποιηθεί autoindex, εκτίθεται όλος ο κατάλογος.

**Διόρθωση:** δεν λύνεται από τον κώδικα PHP — χρειάζεται κανόνας στη ρύθμιση του server:
```nginx
location ~* /wp-content/uploads/ecrm-secure/ { deny all; return 404; }
```
Αυτό που **μπορεί** να κάνει ο κώδικας είναι να το ελέγξει: μια αίτηση HEAD στο ίδιο του το αρχείο κατά την ενεργοποίηση, και προειδοποίηση στην οθόνη διαχείρισης αν επιστρέψει 200. Ένα «είμαι προστατευμένος» που δεν επαληθεύτηκε ποτέ είναι το ίδιο με το `NoRemoteFontsTest` πριν γραφτεί.

## 11. Το backfill του `afm_hash` μπορεί να κατακάτσει σε κρυπτοκείμενο

`src/Persistence/Schema/Migrations/AddCustomerAfmIndex.php:75-99`

```php
$rows = $wpdb->get_results( "SELECT id, afm FROM `{$table}` WHERE afm IS NOT NULL AND afm <> '' AND (`{$column}` IS NULL OR `{$column}` = '')" );
foreach ( $rows as $row ) {
    $wpdb->update( $table, [ CustomerFields::INDEX_COLUMN => $fields->index( (string) $row['afm'] ) ], ... );
}
```

Το docblock (γρ. 17) ισχυρίζεται: *«Κάθε υπάρχουσα γραμμή είναι plaintext σε αυτό το σημείο.»* Αυτό αληθεύει **μόνο** αν το migration τρέξει πριν ανάψει η κρυπτογράφηση. Αλλά:

- η κρυπτογράφηση ανάβει με σταθερά στο `wp-config.php`, **οποτεδήποτε**, ανεξάρτητα από τα migrations·
- το migration τρέχει στο `plugins_loaded` όποτε βρεθεί εκκρεμές (`Installer::maybeUpgrade():78`).

**Σενάριο:** ένα site ανάβει το `ECRM_ENCRYPT_PII` πρώτα. Νέοι και επεξεργασμένοι πελάτες αποκτούν `afm = 'ecrm1:…'`. Μετά ενημερώνεται το plugin, το 0010 τρέχει και υπολογίζει `blindIndex('ecrm1:…')`.

Το αποτέλεσμα δεν σπάει τίποτα ορατό: το `afm_hash` έχει τιμή, το ερώτημα εκτελείται, απλώς **δεν ταιριάζει ποτέ**. Ο έλεγχος διπλότυπων γυρίζει «κανένα διπλότυπο» — και το ίδιο το docblock της κλάσης λέει τι σημαίνει αυτό: *«ο χειρότερος τύπος αποτυχίας, γιατί ο συνεργάτης θα το διαβάσει ως "δεν υπάρχει διπλότυπο" και θα καταχωρήσει δεύτερη αίτηση»*. Και δεν διορθώνεται αναδρομικά, γιατί το plaintext δεν υπάρχει πια πουθενά.

Ο σωστός έλεγχος υπάρχει ήδη στον κώδικα — `CustomerFields::encryptStoredColumns()` (γρ. 203) κάνει `if (FieldCipher::isEncrypted($stored)) continue;`. Το migration δεν τον κάνει.

**Διόρθωση:**
```php
$plain = FieldCipher::isEncrypted((string) $row['afm'])
    ? $cipher->decrypt((string) $row['afm'])
    : (string) $row['afm'];
if ($plain === '') { continue; }
```

**Έλεγχος στην παραγωγή** — αν βγάλει γραμμές, ο δείκτης είναι ήδη χαλασμένος:
```sql
SELECT COUNT(*) FROM wp_ecrm_customers
WHERE afm LIKE 'ecrm1:%' AND afm_hash IS NOT NULL AND afm_hash <> '';
```
(Δεν αποδεικνύει από μόνο του βλάβη — μια γραμμή μπορεί να πήρε σωστό hash από το `forStorage()` και να κρυπτογραφήθηκε μετά. Το οριστικό τεστ είναι: πάρε ένα γνωστό ΑΦΜ, τρέξε `/contracts/duplicate` και δες αν το βρίσκει.)

## 15. Ο migration runner δεν έχει κλείδωμα

`src/Persistence/Schema/MigrationRunner.php:51-75` — καλείται από το `Installer::maybeUpgrade()` σε **κάθε αίτηση** (`plugins_loaded`).

Όταν ένα deploy προσθέτει migration, οι πρώτες N ταυτόχρονες αιτήσεις βλέπουν όλες το ίδιο εκκρεμές και το τρέχουν όλες. Το `markApplied()` (γρ. 99-105) είναι read-modify-write σε option: δύο ταυτόχρονα τερματισμοί μπορούν να χάσουν το ένα id, οπότε το migration ξανατρέχει και τρίτη φορά.

Ο σχεδιασμός είναι κατά τα άλλα σωστός — το `break` χωρίς `markApplied` στο catch είναι ακριβώς το σωστό — και τα περισσότερα migrations είναι idempotent από κατασκευή (ελέγχουν `hasColumn`/`hasIndex`, το backfill φιλτράρει `IS NULL`). Το ρίσκο συγκεντρώνεται στα seed migrations (`SeedMobilePrograms`, `SeedOrizonPlans`, `SeedProtergiaHomePlans`) — αξίζει να επιβεβαιωθεί ότι κάνουν `INSERT ... ON DUPLICATE KEY` ή έλεγχο ύπαρξης.

**Διόρθωση:** ένα transient-lock γύρω από το `run()`:
```php
if ( false === get_transient('ecrm_migrating') ) { set_transient('ecrm_migrating', 1, 120); ... delete_transient(...); }
```
Δεν είναι αδιάβλητο (δεν υπάρχει atomic set-if-absent στα transients με object cache), αλλά κλείνει το ρεαλιστικό παράθυρο. Το `GET_LOCK()` της MySQL είναι το αυστηρό.

# Τι είναι σωστά χτισμένο

Δεν το γράφω για ευγένεια — μετράει για το πού **δεν** χρειάζεται να ξανακοιτάξεις:

- **`FieldCipher`** — XSalsa20-Poly1305 μέσω `sodium_crypto_secretbox`, τυχαίο nonce 24 bytes ανά τιμή, ενσωματωμένο tag αυθεντικοποίησης, **χωριστό κλειδί** για το blind index, versioned prefix `ecrm1:`, άρνηση αντί για σιωπηλό plaintext όταν λείπει το libsodium. Δεν βρήκα τίποτα να πω.
- **`NetworkPath`** — το materialized path έχει διαχωριστικό **και στα δύο άκρα**, με το σχόλιο να εξηγεί ακριβώς γιατί (`/1/7/` να μην ταιριάζει το `/1/70/`). Το επαλήθευσα: το `subtreeIds()` δεν διαρρέει σε γειτονικό υποδέντρο.
- **`UserScope` + `ScopeClause`** — δεν μπορείς να διατυπώσεις ερώτημα συμβάσεων χωρίς να δηλώσεις για λογαριασμό ποιου. Το `placeholders()` δεν γίνεται ποτέ κενό, οπότε το `IN ()` που θα ταίριαζε τα πάντα είναι αδύνατο.
- **`ContractDetails`** — ένα αντίγραφο του join, `private detailed()` ώστε κανείς να μη μπορεί να περάσει δικό του (ή κενό) clause. Ο σωστός τρόπος να κλείσει η διαρροή των τριών αντιγράφων.
- **Οθόνες διαχείρισης** — έλεγξα και τις 16 `admin_post_*` και τη μία `wp_ajax_*`: **όλες** έχουν `current_user_can('manage_options')` **και** `check_admin_referer`/`check_ajax_referer`. Καμία εξαίρεση.
- **`ContractCode::forId()`** — ο κωδικός παράγεται από το auto-increment id, όχι από μετρητή. Δεν υπάρχει race στη δημιουργία κωδικού, που είναι το κλασικό σημείο που σπάει.
- **`SignatureRepository::sign()`** — η συνθήκη «δεν έχει υπογραφεί» μέσα στο `UPDATE`. Το σωστό μοτίβο· λείπει μόνο από τις εκκαθαρίσεις (#1).
- **`ClientIp`** — η ίδια η υλοποίηση είναι υποδειγματική. Λείπει μόνο η καλωδίωση (#8).
- **Το tracking token** — HMAC 80 bits, `hash_equals`, χωρίς εγγραφή στη βάση, μη απαριθμήσιμο.
- **Prepared statements** — σάρωσα και τις 213 κλήσεις `$wpdb->` στο `src/Persistence`. **Δεν βρήκα ούτε μία περίπτωση SQL injection.** Κάθε παρεμβολή είναι είτε `%i`/`%d`/`%s`, είτε fragment `IN (%d,%d,…)` παραγόμενο από `placeholders()`, είτε αναγνωριστικό από κλειστή λίστα (`Tables::*`, `WritableColumns`). Τα `phpcs:ignore` είναι όλα αιτιολογημένα και σωστά.
