# Energy CRM — Αρχιτεκτονική

Ζωντανό έγγραφο. Περιγράφει πού πάμε και γιατί, όχι μόνο πού είμαστε.

Για το τι άλλαξε και με ποιον σκοπό σε κάθε βήμα, δες το
[CHANGELOG](CHANGELOG.md) — εκεί καταγράφονται και τα ανοιχτά θέματα ασφάλειας.

## Αρχές

1. **Το authorization είναι δομικό, όχι κατά περίπτωση.** Δεδομένα συμβάσεων
   φορτώνονται *μόνο* μέσα από repositories που δέχονται υποχρεωτικά τον
   χρήστη. Δεν υπάρχει τρόπος να γράψεις query χωρίς scope, άρα δεν υπάρχει
   τρόπος να το ξεχάσεις.
2. **Ένα αρχείο, μία ευθύνη.** Καμία κλάση δεν ξεπερνά τις ~200 γραμμές. Αν
   μεγαλώνει, κάνει παραπάνω από ένα πράγμα.
3. **Ο domain κώδικας δεν ξέρει από WordPress.** Κανόνες (μεταβάσεις status,
   υπολογισμός προμηθειών, ιεραρχία δικτύου) ζουν σε καθαρές κλάσεις που
   τρέχουν σε unit test χωρίς βάση.
4. **Η βάση αλλάζει μόνο με migrations.** Ποτέ ξανά «κάνε SHOW COLUMNS και δες
   αν λείπει».
5. **Τίποτα δεν σπάει στην πορεία.** Strangler pattern: το νέο layer μπαίνει
   πίσω από τα υπάρχοντα entry points, οι callers μεταφέρονται ένας-ένας.

## Δομή


**Το `class-ecrm-rest.php` δεν υπάρχει πια.** Ο μονόλιθος άδειασε σε επτά
κινήσεις: οι διαδρομές σε controllers (βήμα 6), μετά ο κύκλος ζωής, το
auto-process, η παραγωγή εγγράφων και οι ειδοποιήσεις σε δικές τους κλάσεις, η
νεκρή `can_manage_team()` στα σκουπίδια, και τέλος το `NS` στον `Router` — που
είναι και ο σωστός ιδιοκτήτης, αφού αυτός δηλώνει τις διαδρομές. Ο `no-cache`
πήγε μαζί του.

Η σειρά που το έκανε ασφαλές, και αξίζει να επαναληφθεί σε κάθε επόμενο legacy
αρχείο: **characterisation tests πρώτα πάνω στον παλιό κώδικα, σε δικό τους
commit· μετά νέες κλάσεις με το παλιό ως λεπτό περιτύλιγμα· μετά τα σημεία
κλήσης· τέλος η διαγραφή.** Κριτήριο επιτυχίας: τα tests αλλάζουν **μόνο** στο
ποιον καλούν.

**Οι ειδοποιήσεις πήγαν σε δικές τους κλάσεις, όχι στο `ECRM_Notifications`.** Η
προηγούμενη διατύπωση εδώ έλεγε «συγχώνευση στο υπάρχον `ECRM_Notifications`, όχι
νέα κλάση». Αποσύρθηκε 2026-08-11: οι δύο μοιράζονται μόνο το όνομα. Το
`ECRM_Notifications` στέλνει **email**· οι `ECRM_REST::notify*` γράφουν γραμμές
στον πίνακα `notifications` — το καμπανάκι της οθόνης. Συγχώνευση θα έβαζε δύο
μηχανισμούς σε ένα αρχείο. Το in-app έχει ήδη σπίτι: το `NotificationRepository`
έχει `recentFor`/`unreadCount`/`markRead` και **καμία μέθοδο εγγραφής**.

Προσοχή στο `NS`: **δεν** το χρησιμοποιεί μόνο το `ECRM_Tracking`. Δέκα χρήσεις
σε έξι αρχεία, εκ των οποίων έξι `register_rest_route` σε `ECRM_Tracking`,
`ECRM_KB` και `ECRM_Assistant` — και τα τρία ζωντανά στον `Loader`. Ο πλήρης
πίνακας στο `HANDOVER.md` §6β.3.

## Η HTTP επιφάνεια

Όλα κάτω από `ecrm/v1` (`Router::NAMESPACE`). Ο πίνακας ζούσε ως σχόλιο μέσα στο
`ECRM_REST::routes()` και μεταφέρθηκε εδώ όταν σβήστηκε το αρχείο: ήταν το μόνο
σημείο που απαριθμούσε ολόκληρη την επιφάνεια, και δεν έπρεπε να χαθεί επειδή
έτυχε να ζει σε αρχείο που έφυγε.

| Διαδρομή | Controller |

| `GET /dashboard` | `DashboardController` |

| `POST /contracts/{id}/files`, `GET /file/{id}` | `DocumentsController` |
| `POST /contracts/{id}/renew`, `/renewals` | `RenewalsController` |

**Τέσσερις διαδρομές δεν είναι controllers ακόμη** — τις δηλώνουν legacy κλάσεις
απευθείας, με `Router::NAMESPACE`:

| Διαδρομή | Πού δηλώνεται |
|---|---|
| `/track/{token}`, `/track/{token}/sign`, `/track/{token}/upload` | `ECRM_Tracking` |
| `/kb`, `/kb/ask` | `ECRM_KB` |
| `/assistant` | `ECRM_Assistant` |

**Μια διαδρομή δεν δηλώνεται ποτέ σε δύο σημεία.** Το WordPress κρατά σιωπηλά
όποια καταχωρηθεί τελευταία, οπότε το διπλό `register_rest_route` δεν βγάζει
σφάλμα — αλλάζει απλώς ποιος απαντά.

**Ο no-cache είναι του `Router`.** Κάθε απάντηση κάτω από το `ecrm/v1` παίρνει
`no-store`, μέσω `rest_post_dispatch`. Ο έλεγχος προθέματος κρατά τις κεφαλίδες
μακριά από κάθε άλλο REST API του site.

## Χωρητικότητα

Το ζητούμενο: 2.000 ανοιχτές καρτέλες, 20–40 ταυτόχρονες αιτήσεις, αιχμή στις
100–150. Οι αδρανείς καρτέλες δεν ήταν ποτέ το πρόβλημα — παράγουν ~33 αιτήματα
το δευτερόλεπτο για το καμπανάκι. Το ταβάνι ήταν δύο σημεία που κρατούσαν έναν
PHP worker για δευτερόλεπτα.

| Τι | Πριν | Μετά |
|---|---|---|
| PDF παρόχου | σύγχρονα σε **κάθε** αποθήκευση, 256 MB, ακόμα και σε πρόχειρη | προγραμματισμένο· σύγχρονα μόνο πριν φύγει σύνδεσμος υπογραφής |
| Εξαγωγή AI | 18 δ., απεριόριστες ταυτόχρονες, timeout 60 δ. | 7,5 δ., 12 θέσεις, timeout 30 δ. |
| Εικόνες | ανέβαιναν 4000×3000 / 3–8 MB | σμικρύνονται στα 1600 px στον browser (~300 KB) |
| Λίστα συμβάσεων | filesort σε κάθε φόρτωση | index `(partner_user_id, status, created_at)` |

Δώδεκα θέσεις × 7,5 δευτερόλεπτα ≈ 90 αναγνώσεις το λεπτό, οπότε σαράντα
ταυτόχρονοι συνεργάτες εξυπηρετούνται μέσα σε μισό λεπτό και η ουρά δεν
γίνεται ποτέ ορατή. Η ουρά ζει στον browser, όχι στον server: τα έγγραφα
ταυτότητας δεν γράφονται ποτέ στον δίσκο, και αυτό δεν θυσιάστηκε.

Το επόμενο ταβάνι, αν χρειαστεί: το `no-store` σε κάθε διαδρομή σημαίνει ότι
τα 33 αιτήματα του καμπανακιού σηκώνουν ολόκληρο το WordPress. Με `ETag` θα
γίνονταν 304 χωρίς ερώτημα στη βάση.

## Ορατότητα και ιεραρχία

Τρία ερωτήματα που το CRM συχνά μπερδεύει σε ένα:

- **Ποιος πούλησε** — `contracts.partner_user_id`. Καθορίζει την προμήθεια.
- **Ποιος διαχειρίζεται** — το δέντρο `ecrm_parent`. Καθορίζει την ομάδα.
- **Ποιος βλέπει** — το `UserScope`. Παράγεται από τα δύο παραπάνω συν τα
  capabilities.

Η ιεραρχία αποθηκεύεται ως materialized path στο user meta `ecrm_path`:
`/1/7/23/` σημαίνει ότι ο 23 αναφέρεται στον 7, που αναφέρεται στον 1. Έτσι το
«όλοι κάτω από τον 7» γίνεται `WHERE ecrm_path LIKE '/1/7/%'` — ένα query αντί
για ένα ανά κόμβο. Οι κάθετοι στα άκρα δεν είναι διακοσμητικές: χωρίς αυτές, το
`/1/7` θα ταίριαζε και στο `/1/70/`.

Το `ecrm_parent` παραμένει η πηγή αλήθειας για κάθε ακμή· το `ecrm_path` είναι
παράγωγο και συντηρείται αυτόματα από το `NetworkSync`, που κρέμεται στα meta
hooks — όχι από τους call sites.

**Ο administrator βλέπει όλες τις συμβάσεις της εταιρείας.** Η ιεραρχία αφορά
προμήθειες, όχι δικαίωμα εποπτείας. Ο ιδιοκτήτης δεν χρειάζεται να είναι γονέας
όλων για να δει το σύνολο.

## Αναγνώσεις χωρίς actor

Η αρχή 1 λέει ότι κάθε ερώτημα συμβολαίων δηλώνει για λογαριασμό ποιου τρέχει.
**Έξι μέθοδοι δεν το κάνουν**, σκόπιμα, και η εξαίρεση είναι αρκετά στενή για να
απαριθμηθεί ονομαστικά:

| Μέθοδος | Πού ζει | Γιατί δεν έχει actor |
|---|---|---|
| `statusOf()` | `ContractTransitions` | Φτάνει μέσω `ContractLifecycle`, που οι καλούντές του έχουν ήδη λύσει τη σύμβαση με scoped ανάγνωση |
| `applyTransition()` | `ContractTransitions` | Το ίδιο. Δεύτερος έλεγχος εδώ δεν προσθέτει ασφάλεια — κάνει τον καλούντα να πιστεύει ότι ο έλεγχος ζει εδώ |
| `idsSignedBefore()` | `ContractTransitions` | Σάρωση από cron, για λογαριασμό κανενός. Δεν υπάρχει actor να δεθεί, και αυτός είναι ο λόγος ύπαρξής της |
| `forDocument()` | `ContractDetails` | Cron **και** ο ανώνυμος πελάτης που ακολουθεί σύνδεσμο υπογραφής. Οι δύο REST καλούντες λύνουν πρώτα με `findDetailed()` |
| `noticeSubject()` | `ContractDetails` | Και οι τρεις καλούντες είναι ο πελάτης — ανεβάζει ή υπογράφει. Scope στον **παραλήπτη** θα ήταν ανάποδο, αφού ο παραλήπτης είναι αυτό που ρωτά η ανάγνωση |
| `clearExtractionPayloads()` | `ContractRepository` | Προγραμματισμένη συντήρηση. Μηδενίζει στήλη, δεν διαβάζει και δεν μετακινεί δεδομένα |

**Το κριτήριο εισδοχής, γραμμένο ώστε να μη χρειάζεται κρίση:** μέλος που **έχει**
actor δεν ανήκει εδώ. Δεν υπάρχει τέτοιο μέλος, και η προσθήκη ενός είναι αυτό
που πρέπει να απορριφθεί.

Η ιστορία της ομάδας είναι ο λόγος που ο κανόνας γράφτηκε έτσι. Ονομάστηκε
«lifecycle» όταν είχε τρία μέλη. Στις 2026-08-10 ήρθε το τέταρτο και τέθηκε το
ερώτημα αν η εξαίρεση είναι ακόμη εξαίρεση· η απάντηση ήταν ότι η κοινή ιδιότητα
δεν ήταν ποτέ «lifecycle» αλλά «**τρέχει για λογαριασμό κανενός**» — cron και
ανώνυμος πελάτης, και τα δύο. Στις 2026-08-11 ήρθε το πέμπτο, μετρήθηκε με το
ίδιο κριτήριο, και προτιμήθηκε από το να μείνει πέμπτο χειρόγραφο
`contracts`+`customers` join στη βάση κώδικα — το σχήμα που είχε μόλις κοστίσει
τρεις διαρροές PII.

Ομάδα που το όνομά της δεν περιγράφει πια τα μέλη της είναι ο τρόπος που μια
στενή εξαίρεση γίνεται γενική χωρίς να το αποφασίσει κανείς. Γι' αυτό ο πίνακας
είναι εδώ, ονομαστικός, και όχι σχόλιο μέσα σε ένα αρχείο.

## Μεγέθη κλάσεων — και πού σταματά ο κανόνας

Το όριο των ~200 γραμμών είναι ευρετικό, όχι νόμος, και ο `ContractRepository`
είναι το σημείο όπου φάνηκε η διαφορά.

Ήταν 930 γραμμές. Σπάστηκε σε πέντε κλάσεις, καθεμιά ονομασμένη από την ιδιότητα
που ομαδοποιεί τα μέλη της: `ContractQueries` (οι λίστες), `ContractDetails` (το
join, και το μοναδικό του αντίγραφο), `ContractTransitions` (χωρίς actor),
`WritableColumns`, `ScopeClause`. Ο `ContractRepository` κρατά το scoped CRUD
ενός συμβολαίου και προσγειώνεται γύρω στις **430**.

**Δεν πάει στις 200, και δεν πρέπει.** Για να φτάσει θα έπρεπε να σπάσει και το
CRUD σε `ContractReader` / `ContractWriter` / `ContractDeleter`. Το κόστος:
περισσότερα σημεία που αγγίζουν τον πίνακα, περισσότερο wiring σε κάθε
controller, και — το σοβαρό — η εγγύηση «ένα σημείο πρόσβασης, που δεν μπορεί να
γράψει ερώτημα χωρίς scope» αραιωμένη σε οκτώ αρχεία αντί για ένα.

Ο κανόνας υπάρχει για να πιάνει κλάσεις που κάνουν **παραπάνω από ένα πράγμα**.
Ο `ContractRepository` κάνει ένα: πρόσβαση σε μία οντότητα, με υποχρεωτικό actor.
Όταν το όριο και ο σκοπός του διαφωνούν, κερδίζει ο σκοπός — και καταγράφεται,
ώστε ο επόμενος να μη το ξαναπροσπαθήσει νομίζοντας ότι κάτι ξεχάστηκε.

## Προσωπικά δεδομένα

Το CRM κρατά ΑΦΜ, ΑΔΤ, διευθύνσεις, IBAN, σαρωμένες ταυτότητες και εικόνες
υπογραφής. Δύο κανόνες που δεν είναι προφανείς από τον κώδικα:

**Ένα σημείο ξέρει πού ζουν.** Ο `PersonalDataEraser` είναι ο μόνος που
γνωρίζει ποιες στήλες σε ποιους πίνακες περιέχουν προσωπικά δεδομένα. Οθόνη που
χρειάζεται διαγραφή τον καλεί· δεν γράφει δικά της queries. Προσθέτεις πίνακα με
προσωπικά δεδομένα — τον προσθέτεις εκεί, αλλιώς η διαγραφή τον αφήνει πίσω και
κανείς δεν το βλέπει.

**Το `extra_json` είναι default-deny.** Το bag δέχεται όποιο key στείλει η
φόρμα, άρα δεν μπορεί να υπάρξει πλήρης λίστα προσωπικών πεδίων. Η
`ProviderFormFields::NON_PERSONAL_INPUTS` απαριθμεί το αντίθετο: τι επιτρέπεται
να επιβιώσει μιας διαγραφής. Ό,τι δεν είναι εκεί θεωρείται προσωπικό. Νέο πεδίο
σε φόρμα παρόχου σβήνεται σωστά χωρίς να το θυμηθεί κανείς — και αν είναι όντως
τεχνικό, μπαίνει ρητά στη λίστα.

Η διαγραφή είναι **ανωνυμοποίηση, όχι εξαφάνιση**: οι γραμμές των συμβολαίων
μένουν χωρίς τις προσωπικές τους στήλες, ώστε να μετριούνται ακόμα.

**Κρυπτογραφημένες στήλες και blind index.** Το `CustomerFields` ορίζει ποιες
στήλες πελάτη αποθηκεύονται κρυπτογραφημένες (`afm`, `adt`, `street`,
`street_no`, `postal_code`) και μεταφράζει προς τις δύο κατευθύνσεις. Κάθε
query που επιστρέφει αυτές τις στήλες — και μέσω join — περνά από εκεί, αλλιώς
ο συνεργάτης βλέπει base64 αντί για ΑΦΜ.

Επειδή η κρυπτογράφηση είναι τυχαιοποιημένη, το `WHERE afm = %s` δεν ταιριάζει
ποτέ. Γι' αυτό υπάρχει το `afm_hash`: keyed hash της ίδιας τιμής, σταθερό, που
κρατά ζωντανό τον έλεγχο διπλοεγγραφών και την αναζήτηση με πλήρες ΑΦΜ.
Αναζήτηση με **μερικό** ΑΦΜ δεν επιβιώνει — ένα hash δεν έχει πρόθεμα.

Η εγγραφή ciphertext είναι opt-in (`ECRM_ENCRYPT_PII` στο `wp-config.php`)· η
ανάγνωση καταλαβαίνει και τα δύο, ώστε να μην υπάρχει ημέρα σημαία.

Τα έγγραφα δεν σερβίρονται ποτέ απευθείας. Ζουν στο `uploads/ecrm-secure` με
`.htaccess` + `web.config` που το αρνούνται, με μη μαντεύσιμα ονόματα, και
φτάνουν στον χρήστη μόνο μέσω υπογεγραμμένου token με έλεγχο scope. Ό,τι
απέμεινε από παλιά στη media library το μεταφέρει σταδιακά το
`DocumentProtection`.

## Αλλαγές στη βάση

Δύο μηχανισμοί, με σαφή διαχωρισμό ευθύνης:

- **`dbDelta`** δημιουργεί τους πίνακες σε καθαρή εγκατάσταση. Το αφήνουμε να
  κάνει μόνο αυτό.
- **Migrations** (`src/Persistence/Schema/`) κάνουν ό,τι το dbDelta δεν μπορεί:
  foreign keys, indexes, μετατροπές δεδομένων, διαγραφές στηλών.

Ο λόγος του διαχωρισμού: το dbDelta είναι «κάνε το schema να μοιάζει έτσι»,
αναλύει CREATE TABLE με regex και **σιωπηλά αγνοεί** ό,τι δεν καταλαβαίνει —
γι' αυτό υπήρχε το `ensure_columns()` με τα χειροκίνητα `SHOW COLUMNS` σε κάθε
request. Ένα migration αντίθετα είναι «κάνε αυτή τη συγκεκριμένη αλλαγή, μία
φορά», και καταγράφεται.

**Ποτέ σχόλια `--` μέσα στα statements του dbDelta.** Δεν κάνει parse SQL:
διαβάζει γραμμή-γραμμή και θεωρεί ό,τι ακολουθεί το όνομα της στήλης ως ορισμό
της, σχόλιο συμπεριλαμβανομένου. Το ALTER που παράγει είναι άκυρο και
απορρίπτεται — σιωπηλά, γιατί το `$wpdb` κρύβει τα σφάλματα στην παραγωγή. Αυτή
ήταν η αιτία του «σιωπηλά αγνοεί» παραπάνω, και βρέθηκε μόλις η σουίτα
integration έστησε τους πίνακες σε καθαρή βάση. Το λεξιλόγιο των στηλών ζει σε
σχόλια PHP πάνω από κάθε `dbDelta()`.

Κανόνες:

- Το `id()` ενός migration **δεν αλλάζει ποτέ** μετά την κυκλοφορία. Είναι το
  μόνο πράγμα που λέει σε ένα live site ότι κάτι έχει ήδη τρέξει.
- Η λίστα στο `MigrationList` είναι **append-only**.
- Κάθε migration ρωτάει τον `SchemaInspector` πριν αλλάξει, ώστε να είναι
  σωστό και σε καθαρή εγκατάσταση και σε αναβάθμιση.
- Migration που αποτυγχάνει **δεν καταγράφεται**: ξαναδοκιμάζει στο επόμενο
  request αντί να αφήσει το schema σε κατάσταση που δεν περιέγραψε κανείς.

## Coding standard

`src/` και `tests/` ακολουθούν **PSR-12**, όχι WordPress-Core. Ο λόγος: οι
κανόνες τεκμηρίωσης του WPCS (`@var`, `@param` παντού) γράφτηκαν για κώδικα
χωρίς type declarations, όπου το docblock ήταν η μόνη πληροφορία τύπου. Με
native types γίνονται διπλοεγγραφή που σαπίζει. Ομοίως τα short arrays και οι
Yoda conditions είναι κατάλοιπα της PHP 5.x.

Κρατάμε από το WPCS ό,τι πιάνει πραγματικά bugs: `WordPress.Security`
(escaping, nonces, sanitization) και `WordPress.DB` (prepared statements).

Ο legacy κώδικας σε `includes/`, `admin/`, `public/` μπήκε στο ruleset τις
2026-08-10, αλλά **μόνο για τους sniffs ασφαλείας** — escaping, nonces,
sanitisation, prepared SQL. Το PSR-12 μένει κλειστό εκεί: μερικές χιλιάδες
ευρήματα για tabs και Yoda conditions θα έθαβαν τη χούφτα που μετράει, και τα
αρχεία σβήνονται ένα-ένα καθώς μεταναστεύουν. Το `.editorconfig` κρατά tabs
εκεί και spaces στο `src/`, ώστε να μη γεμίσουν τα diffs με αλλαγές κενών.

## Development

```bash
composer install                      # dev tooling μόνο — το plugin τρέχει και χωρίς vendor/
git config core.hooksPath .githooks   # μία φορά ανά clone
composer check                        # phpcs + phpstan + phpunit
```

Ο pre-commit hook τρέχει το `composer check` και μπλοκάρει το commit αν
αποτύχει. Παράκαμψη μόνο συνειδητά, με `git commit --no-verify`.

Τα unit tests δεν φορτώνουν WordPress. Αν μια κλάση δεν τεστάρεται χωρίς
WordPress, είναι σήμα ότι ανακατεύει domain λογική με infrastructure.

Ό,τι *πρέπει* να μιλήσει με βάση — scope, SQL, κρυπτογραφημένες στήλες,
διαγραφή — ζει στη σουίτα integration, με δική της βάση μιας χρήσης:
`composer test:integration`. Δες [TESTING](TESTING.md). Δεν μπαίνει στο
`composer check` ώστε να μπορεί να κάνει commit και όποιος δεν την έχει στήσει.
